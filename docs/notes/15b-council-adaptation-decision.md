## 3. Существенные разногласия (сохранены с атрибуцией)

1. **Q1: GO (прагматик) vs CONDITIONAL (аудитор, архитектор, реалист, скептик).** Прагматик: каркас уже доказан «в гневе» (окно, dirty-ro). Остальные: каркас ещё не обёрнут вокруг каждой сессии; sentinel-хэши, RSS-цензус, pjdfstest-контракт не написаны. Разрешение: спор о моменте, не о модели — каркас = фаза 0, сессии только после.
2. **Топология стейджа: 1 член (архитектор: прод-топология на file-backed всё равно невоспроизводима) vs 2 члена с метками nvme/hdd (аудитор, прагматик, реалист: multi-device в батарее доказан только на 256–512M образах — стейдж растит покрытие бесплатно).** Решение: 2 члена.
3. **Число копий: одна расходуемая (большинство) vs вторая замороженная эталонная (скептик).** Решение: одна рабочая + ZFS-снапшот zvols до первого маунта (= замороженный эталон посева) + манифест с выборочными sha256 + снапшоты pre/post каждой сессии.
4. **Срок бэкапа незаменимого: до первой write-heavy сессии даже на стейдже (скептик: индекс/курация STASH станут work product) vs до первого rw живого пула (аудитор, прагматик, реалист).** Решение: копию запускать сейчас (единодушие: «самое дешёвое из самых ценных»); жёсткий гейт — первый rw живого пула; риск скептика погашен выносом БД/индексов STASH на ZFS хоста.
5. **Пост-cutover календарь: скептик сохраняет 24h soak ступени + 30 дней прод-soak; остальные заменяют счётчиками (k чистых сессий).** Решение: счётчики + первая неделя прода с усиленным мониторингом и правом немедленного разворота; спор зафиксирован — настройка гейтов прода отдельным решением перед фазой 5.
6. **B1 in-place vs B2 migration:** реалист вводит B2 как равную ветку (убивает формат-риск и «тающий откат» ценой полной перекачки); остальные неявно предполагают B1. Решение: ветка выбирается тремя измеримыми фактами (Q3), не предпочтением.

## 4. Решение

### Q1 МОДЕЛЬ АДАПТАЦИИ — **CONDITIONAL** (после фазы 0 — GO)

Модель: прогресс = экспозиция (ops, ГБ, сессии, покрытие классов операций), не календарь. «Чиним на лету» разрешено для кода, запрещено для данных.

Условия:
1. Каркас автоматических гейтов (фаза 0, §5) построен и всухую прогнан ДО первой сессии нагрузки.
2. Классификация находок: перф/errno/cosmetic → fix-on-the-fly; **corruption-class (порча/чексумма на диске) → write-freeze + kill-review**; kill-критерии §8 абсолютны и не адаптируются.
3. Правило «фикс → тест в батарею → счётчик заново»: каждый фикс приземляется с тестом, падающим на пре-фикс артефакте (паттерн 045/046/047) — батарея монотонно ужесточается, это и есть замена монотонности 14 дней.
4. Стартовые экспозиционные пороги (настроить по первому ledger'у): ≥1 полный скан библиотеки или ≥10⁷ файлo-визитов; ≥5×10⁵ create; ≥3 чистые kill-9-дрели под реальной формой нагрузки; ≥10 последовательных чистых session-end fsck; RSS — плато или капнута.
5. Пиннинг билда: бинарь пересобирается только на границах сессий; sha256 в ledger; `regression.sh quick` перед каждым продвижением.

**Первый шаг:** расширить `scripts/regression.sh` (sentinel-стадия ~64 стратифицированных хэшей; RSS-захват; оп-цензус из `BCACHEFS_FUSE_LOG`; еженедельный pjdfstest) + скрипт-обёртка сессии. Всё до посева стейджа.

### Q2 ПЕРВАЯ НАГРУЗКА — stash-GPU на стейдже — **GO**

Дизайн (конвергенция пяти докладов):
- **Носитель:** 2 file-backed члена на zvols zdata (метки nvme/hdd), суммарно 0.5–1T; исключение из «тест-образы ≤2G» подписано владельцем (15a, фаза 2). Размер — по `zfs list` (3.11T свободно).
- **ZFS-снапшот zvols до первого маунта** = кнопка сброса и замороженный эталон посева.
- **Посев:** `rsync -aH --delete --checksum` (часы гостя дрейфят +6ч20м — только чексуммы, не время), **без `-X`** (extattr vnops нет), через NFS-мост при **работающей** VM (хост-собственные zvols — конфликта эксклюзивности нет), throttled (`nice`, `--bwlimit`) вне пика; манифест + выборочные sha256 в ledger. Далее: ночная дельта, недельный полный reconcile.
- **Поток односторонний:** прод → стейдж всегда; стейдж → прод никогда (до решения cutover). Стейдж = slave; его выводы — advisory.
- **Раскладка:** `library/` (расходуемый кэш, чтение) + `stash-out/` на FUSE (thumbs/индексы); SQLite/БД/кэш STASH — **на ZFS хоста** (обход открытого mmap-вопроса).
- **Обёртка каждой сессии (автоматически):** mount под `rlimit-run.sh` (rctl `memoryuse:deny`; стартовый кап 1 ГБ — калибровать по стационару ledger'а) → zfs snapshot pre → сессия (`BCACHEFS_FUSE_LOG` вкл) → umount → **bcachefs fsck-гейт** (nonzero = сессия провалена, счётчики обнуляются) → snapshot post + RSS-сэмпл в ledger.
- **Фазирование:** A — scan-only (read-soak по метаданным, слабейшая зона: ×10.7 к мосту); B — запись (`stash-out/` на FUSE) после зелёной A; DB-on-mount — только после mmap-аудита (15a §0.8), по умолчанию не требуется.
- **fd-057 НЕ блокирует rw-стейдж** (rw-fd на rw-маунте легитимен; 057 — гарантия ro-окон живого пула). 057 уже в дереве; для следующего касания живого пула нужны: новая battery-assertion «при ro-маунте все fd членов O_RDONLY по procstat» (батарея [4/5] доказывает только kernel EROFS) + одно повторное чистое ro-окно (внешний счётчик записей + supers bit-bit).
- **Дрель одноразовости ДО первой GPU-сессии:** snapshot-clone → mount → verify → re-rsync поддерева — одноразовость доказана делом, не заявлена.
- **Ресурсы:** один тяжёлый процесс; fsck стейджа под капом 1 ГБ; GPU-окна согласуются с llama-zoo.

**Первый шаг:** создать zvols → снапшот → ночной посев через мост (VM работает, нулевое касание членов пула) → дрель одноразовости.

### Q3 ПУТЬ К CUTOVER — **CONDITIONAL** (дерево)

**Ветка A — расхождение-провал** (любое из): чексумма на ro-чтении; второй corruption-класс после 045/046/047 (паттерн, не случайность); RSS неограничен под капом (утечка, не кэш) → порт = ro-инструмент + research fork; VM не уходит. Честный выход, не позор (публичный репо уже живёт).

**Ветка B — сходимость** (батарея зелёная на каждом фиксe, экспозиция закрыта, RSS плато/кап, порчи нет):
- **B1 cutover-in-place** (базовая): одно окно — VM off → baseline **снять после выключения VM** (урок окна №2) → (opt) ro-verify [057 ✓ + battery-assertion + повторное ro-окно] → rw-маунт живого пула → флип `poolmount` (единственная флип-точка) → сервисы по нарастающей, samba последней → откат ≤30 мин отрепетирован (45 с уже показано).
- **B2 cutover-by-migration** (если dump-super diff противоречив ИЛИ использованный объём пула ≤ ~3T): свежая ФС нашим билдом на тех же дисках после эвакуации через zdata-буфер; старая ФС = натуральный бэкап до декомиссии; убивает формат-риск (1.39.4 vs 1.39.7) и тающий откат ценой полной перекачки.
- **Выбор B1/B2 — три факта** (снять заранее, один вечер): dump-super format/compat diff наш билд vs VM-тулчейны; измеренный использованный объём пула; пиннинг дисков по серийникам (`camcontrol`; закрывает и конфликт ada0/ada1).
- **Необратимость — тающий актив:** точка невозврата = первый rw-маунт живого пула; внутри B1 — первый incompat-бит, написанный нашим билдом за пределами возможностей VM-тулчейнов (проверка compat-битов в момент cutover). После нативных записей откат = «VM-fsck чисто на пуле, который писали мы» — доверие, не бит-компар; пока двойное попечительство желательно — ежемесячный VM-fsck нативного пула.
- **VM — единственный ремонтный цех** (наш fsck детектировал, но ни разу не чинил реальные повреждения): VM **не декомиссионируется, пока наш порт — писатель**. «Пенсионирование» = вывод **моста** из обслуживания; VM → cold-standby навсегда (стоит ≈ диск). Вывод VM даже из cold-standby — отдельное позднее решение; условия: (a) restore-дрель из бэкапа PASS; (b) все 6 сервисов на реальных данных нативно, мониторинг зелёный; (c) подпись владельца на деградациях chflags/extattr.

**Первый шаг:** снять три факта (dump-super diff; использованный объём; camcontrol-пиннинг).

### Q4 БЭКАП-ПОЗИЦИЯ — **NO-GO сегодня; переход в GO по чек-листу**

Статус: перечень незаменимого не составлен, копии нет, restore не пробовался (проверено по всем докам; 15a #13 — открытый вопрос владельцу). Сегодня нетронутый ro-пул сам себе бэкап — именно поэтому модель владельца безопасна для старта.

Условия перехода в GO:
1. **Владелец перечисляет незаменимое подмножество** (photos/home vs перекачиваемое) — только он знает.
2. Одна **чексуммированная** копия на zdata — физически отдельный диск от обоих членов пула; отдельность — **по серийникам** (camcontrol), не по именам.
3. Одна **выполненная проба восстановления** (выборочный restore). «Бэкап = то, что один раз восстанавливали».
4. Процедура письменно; версии — zfs-снапшоты бэкап-датасета (нативные снапшоты bcachefs на BSD невозможны, патч 019).

Жёсткий гейт: до первого rw живого пула (вход в B1/B2). Staging-фазы бэкапа не требуют (пере-выводимость = бэкап по построению). Off-box копия незаменимого (photos) — рекомендация, вопрос владельца.

**Первый шаг:** запустить копию незаменимого через мост **сейчас**, параллельно всему (мост жив, VM работает, нулевой риск/эксклюзивность) + запросить у владельца перечень. Самое дешёвое из самых ценных действий на столе — независимо от исхода всего остального.

## 5. План постепенной адаптации (гейты вместо календаря)

**Инварианты через все фазы:** живой пул не-rw до гейтов Q3+Q4; kill-критерии §8 абсолютны; каждый фикс = патч + тест в батарею + счётчик заново; corruption-находка = write-freeze; бинарь пиннингуется sha256; стейдж одноразовый, поток прод→стейдж односторонний; тяжёлые операции сериализованы, под `nice 19` и rctl-капами.

**Ф0 Каркас** (блокер всех сессий): расширение `regression.sh` (sentinel ~64 хэшей, стратифицированных по глубине; RSS-захват; оп-цензус лога; kill-дрель под нагрузкой; еженедельный pjdfstest + чекпоинт-fsck + umount/remount-дрель); скрипт-обёртка сессии; rctl-кап; канарейка statfs+touch (stall >10 с → алерт, на прод-ступенях авто-`umount -f`). Слои стопа: L0 канарейка → L1 rctl-кап → L2 sentinel/fsck → L3 §8 kill-критерий. *Выход:* обёртка всухую зелёная на пустом стейдже; красная ночь батареи автоматически блокирует продвижение ступеней.

**Ф1 Стейдж + посев** (параллельно: старт Q4-копии через мост; запрос перечня незаменимого; три факта Q3): zvols → снапшот → посев через мост → манифест → дрель одноразовости (snapshot-clone → mount → verify → re-rsync). *Выход:* манифест сверен; дрель зелёная; обёртка возвращает ненулевой код на грязном образе.

**Ф2 stash scan-only** (read-soak метаданных): сессии в обёртке; ответ на RSS-вопрос в «событиях на ГБ чтения» (разделение плато-кэш vs линейная утечка: повторное чтение того же рабочего множества vs свежего). *Гейты:* полный скан библиотеки чисто; 0 необъяснённых аномалий лога; fsck чист после каждого umount; RSS плато/кап.

**Ф3 stash запись** (`stash-out/` на FUSE; БД на ZFS): плановая kill-9-дрель ПОД сканом; p99-гистограмма из ops-трейса против базовой линии; счётчики create/rename/unlink/ГБ. *Гейты:* порча = freeze (без исключений); стартовые пороги экспозиции Q1-4 достигнуты; A/B против моста — побочный продукт (мост живёт).

**Ф4 Мульти-сервис стейдж** (лестница 15a, stash вытянут на первое место): navidrome (read-mostly + теги; постоянный канареечный потребитель) → qbittorrent (write-storm, ближайший к форме regression ст.3) → amuled/amutorrent (long-tail мелкие записи) → **samba последней** (extattr-деградация подписана владельцем). Ступень = k чистых сессий с покрытыми классами ops ступени (не 24h soak); откат ступени = config-flip на NFS-путь.

**Ф5 Cutover:** решение B1/B2 по трём фактам → окно по window-протоколу (baseline после VM-off; supers bit-bit; внешний BIO-счётчик на первые прод-часы записей; откат ≤30 мин отрепетирован) → по-сервисный прод, samba последней → первая неделя усиленного мониторинга с правом немедленного разворота (замена «30 дней soak»; настройка гейтов прода — до фазы) → мост в cold-standby. **VM — навсегда cold-standby** (единственный ремонтный путь; см. Q3).
