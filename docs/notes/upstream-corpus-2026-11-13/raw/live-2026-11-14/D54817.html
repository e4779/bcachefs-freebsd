In D54817#1283360, @imp wrote:
In D54817#1282021, @fedward_gmail.com wrote:

Frankly, I don't think this policy is strong enough. "You are responsible" doesn't have any teeth. What happens when somebody makes a contribution that they're "responsible" for that plagiarizes from copyrighted code and/or violates a license? How is FreeBSD protected when somebody "considers" licensing and decides they don't care?

It's the same thing we face when people copy linux drivers. It's nothing new. Responsibility lies with the tool users.

It is not at all the same thing, because the risk associated with it isn't properly assigned. You can say that the person who uses the tool bears responsibility for the contribution that used it, but there is no way to assign accountability. For the sake of argument, what happens if a person's "due diligence" fails to turn up the fact that their AI-contributed code infringes on copyrighted code (perhaps because that code isn't publicly visible but was nonetheless present in the coding agent's training set; perhaps because the person just didn't do proper due diligence). Who bears legal and financial responsibility for that infringement?

I like the proposed policy in D50650. What was wrong with it?

It was unworkable. AI isn't some binary 'one shot that produced code' but a thousand different ways that AI can help the developer. The vast majority of them are fine and pose no risk whatsoever outside the system that the AI is being run on. So banning it entirely is a non-starter. That ship has sailed. Outlining responsible use is really the only path forward today.

There is no currently accepted way to "prove" that an AI assisted contribution is non infringing, and there is still significant uncertainty around whether AI assisted code can even be copyrighted at all. Accepting AI-assisted code contributions now, before a relatively stable legal framework is established around it, introduces legal and financial risk both to the project that accepts the code and to the end users of that project. I don't know how you're determining what a "vast majority" are, or how you can claim that they "pose no risk," because literally all I see is risk. Accepting AI contributions before there's a way to "prove" them is an unworkable problem.

And sure, you can say "it's good enough for IBM and Red Hat / Canonical and Ubuntu / Microsoft / Amazon" but they have vastly more resources to deal with legal, financial, or coding challenges that may later appear as precedents are established. FreeBSD is already a very small player in comparison to that landscape, and I think the potential risks are not worth the perceived value. If you think FreeBSD should accept those contributions, then before you do that you need to figure out a gameplan for how you can prove code is acceptable and copyrightable, how can pay the legal fees if you get sued, and how you can deal with the sudden absence of an accepted feature if the only way to resolve any infringement is just to yank out the change and revert to how things were before it was accepted.

2414

I am not sure which phrasing sounds more natural to native speakers, but I would prefer Contributions Using Generative AI Tools.

2416

This section should be interpretable even without D54366. Are the following sentences too long to describe the motivation of this section?

Contributions created with the assistance of generative AI tools require special care. The FreeBSD Project assumes that contributions are works created by humans. FreeBSD Project consists of copyrighted works contributed by many individuals and distributed under the BSD license. Under the legal interpretations currently widely accepted internationally, a work distributed under the BSD license must be created through human creativity.

Outputs lacking human creativity are not unique to generative AI tools; automatically generated tables and compiler outputs are also examples of non-human-generated artifacts. However, tools that existed prior to generative AI generally performed deterministic data transformations explicitly directed by humans and did not produce results beyond what the user could reasonably anticipate. In contrast, generative AI tools produce outputs by probabilistically combining information contained within trained models, which means they may generate content that the user did not intend.

As a result, there is a risk that a contribution produced using generative AI may unintentionally infringe on the copyright of others or contain technically incorrect content. All committers must exercise caution regarding these risks. When committing to the FreeBSD repository, please ensure that you comply with the following requirements:
2418

L.2418 and L.2419 basically say the same thing in a different expression. I would say the following single sentence is sufficient:

As with any contribution you create yourself, you must fully understand and review every part of the content being committed. Do not commit generated content without careful verification.
2420

This should come first before L.2418. I believe some more details would be good for this item, like the following to emphasizing the project's requirements:

Review the terms and conditions of any AI tool used for generation, and confirm that the licensing terms of the generated output are compatible with the requirements of the FreeBSD Project. In particular, you must be able to hold the copyright to the contribution and distribute it under the BSD license. Additional attribution requirements imposed by the AI tool are acceptable as long as they remain compatible with the BSD license.
2421

I think privacy is out of scope here and this should be omitted. Entering source code fragments into a Google search is fundamentally the same issue. Committers must exercise appropriate caution, and their working environments should be reasonably secured---they should not paste SSH private keys into public services, even if those services claim to protect user privacy. However, this is not specific to AI tools. If we want to include this topic, it should be elsewhere in this guide.
